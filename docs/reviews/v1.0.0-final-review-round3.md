P1-1 — stale verdict 仍未彻底关闭

现在是：

Python
运行
if 轮次 is not None and 轮次 < self.轮次:
    return ...

这只能防住“明确携带旧 round”的裁定，但还存在三个洞：

旧裁定不带 轮次
→ 直接绕过 stale check

当前 self.轮次 = 2
裁定传 轮次 = 3
→ 也被接受

同一 round 内发生 reopen
→ 旧裁定和新 generation 的轮次相同
→ 仍可消解新 generation

尤其第三种说明本质问题还在：round ≠ issue generation。

例如：

Python
运行

issue: 待复核
收裁定(... 已消解, 轮次=2)

收回执(...)
# → 待复核

# 延迟到达的旧 round-2 verdict
收裁定(... 已消解, 轮次=2)
# 当前实现仍接受

因此原 P1-1 只能算“部分修复”。

真正稳固的形式应是：

(issue_id, generation, attempt_id)

至少裁定要携带：

Python
运行
expected_generation
# 或 expected_attempt

并做 equality CAS，而不是 < self.轮次。

P1-2 — 回执“幂等”仍然不是 identity-based idempotency

当前：

Python
运行

用自然语言内容充当 idempotency key，会同时产生两个相反的问题。

重复请求可以轻易穿透：

第一次："已修改公式"
retry："已修改公式 "
retry："已经修改公式"

都会再次：

Python
运行

于是 crash/retry 仍可能制造假 attempts → 提前熔断。

反过来，合法的新 attempt 又可能被错误吞掉：

attempt 1:
改动 = "已重新计算"
→ reviewer 未消解

attempt 2:
确实重新改了一次
改动仍 = "已重新计算"

→ 被当 duplicate
→ 不进入待复核
→ 尝试次数也不增加

所以这不是可靠幂等键。

这里仍然需要：

运行
receipt_id
# 或
attempt_id

P1-3 — 搁置条目() 可以直接绕过所有 blocker 和熔断条件

当前：

Python

没有检查：

当前状态；

尝试次数 >= 熔断阈值；

是否属于 熔断候选()；

理由是否为空；

是否经过专门 waiver / adjudication。

而 收敛() 又明确不阻塞 搁置。

因此：

也就是说：

否则所谓“熔断候选”只是 advisory，不是 invariant。
