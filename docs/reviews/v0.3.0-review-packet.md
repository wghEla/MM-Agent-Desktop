## 3. Key behaviors

- 错误归一：429→RateLimitError(retry_after_s from Retry-After header, retryable)；
  401/403→auth；5xx→server(retryable)；4xx→bad_request；网络/超时→network(retryable)。
- 工具归一：每协议的工具定义/调用/结果形状双向映射到 NormalizedTool/ToolCall/Message。
- 能力诚实：CapabilitySet 声明各协议真实能力；streaming 全部 False（未实现，不伪装）；
  reasoning_levels 按协议如实（gemini 空；openai_chat 不含 xhigh）。
- 密钥：providers 表只存 api_key_ref；redact_secret() 统一脱敏出口；
  anthropic 用 x-api-key；openai 用 Bearer；gemini 用 x-goog-api-key。
- role_routing：role_id → model_profile → provider；未配置回落 default。

## 5. Known limitations（诚实）

1. 无 streaming（v0.3.x）；capabilities 已如实声明 False。
2. 无真实 Provider 验证（无 key）——所有协议为 offline contract-tested。
3. anthropic thinking 预算映射未实现（reasoning 档→budget_tokens 映射在 role routing 层，v0.4 接入 AgentLoop 时落地）。
4. gemini functionCall 无独立 id：以 name 代替（并行同名调用会有歧义，文档已注明）。
5. test_connection 的探测端点按各协议惯例选择（/models 或 1-token 消息）。

## 6. Focused questions

1. openai_chat 的 reasoning_effort 传法：仅当用户配置了 reasoning 时加字段，模型族不支持时由服务端报错——是否应改为按 model 名前缀猜测支持性（反对：猜测=伪装）？
2. anthropic max_tokens 默认 8192 是否合适（Anthropic 要求必填）？
3. gemini 以 functionCall.name 充当 call_id 的歧义是否可接受（并行同名调用场景在 v0.3 的 MM 流程中不存在）？
4. openai_compatible 的 auth_style 三态（bearer/x-api-key/none）是否足够？
5. RateLimitError 的 retry-after 解析（仅支持秒数，不支持 HTTP-date）是否可接受？
