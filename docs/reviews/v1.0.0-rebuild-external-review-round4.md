## P1-1 — G5 failed figure transaction could fall through to Writer-only repair

**FOUND at `f17d248`; SOURCE-FIXED; REGRESSION PENDING.**

The G5 figure path correctly implemented:

```
Plotter receipt
→ Runtime plot execution
→ guarded Writer dependent-text sync
→ Runtime ledger receipt
```

However, after a failed figure transaction the later text route selected every active
blocking Issue whose target was not `算`:

```python
if x.目标 != "算"
```

That included `目标 == "图"`.

Therefore a figure Issue whose plot transaction failed could subsequently enter the
Writer-only text route. If that Writer leg succeeded, the Issue could receive a repair
receipt and move to `待复核` without a valid figure transaction.

This was a real bypass of the Round-3 P1-B invariant.

### Source fix

The G5 text route now selects **only**:

```python
x.目标 == "文"
```

A figure Issue can advance only through the full figure transaction.

### Required distinguishing regression

Add/adjust a test where:

1. G5 Plotter writes a valid receipt;
2. Runtime plot execution or figure-sync fails;
3. a subsequent Writer-only response is available and would succeed if invoked;
4. assert the figure Issue remains active with no ledger receipt;
5. assert the Writer-only G5 text route was not used for the figure Issue.

## R4-F2 — One S5 calc/figure Issue could be consumed by multiple question transactions

**SOURCE-FIXED; REGRESSION PENDING.**

Normal S5 repair previously added the same Issue to every question number discovered in
its text. An Issue mentioning multiple question numbers could therefore be processed by
multiple transactions in one generation, producing multiple distinct receipts and
inflating attempt accounting.

Source fix:

- calc/figure Issue routing now requires exactly one related question;
- zero or multiple related questions remain active/unrouted;
- the reviewer must split a genuinely multi-question defect into distinct Issue identities.

Add a focused test proving one multi-question Issue cannot receive multiple receipts or
increment attempts twice in one round.

## R4-F3 — S5 round checkpoint preceded post-rework compile/fix

**SOURCE-FIXED; REGRESSION PENDING.**

The master-plan 18-step round order requires:

```
rework
→ guards
→ compile/fix
→ round checkpoint
```

The implementation previously checkpointed immediately after rework and deferred compile
to the beginning of the next review round.

This remained fail-closed at publication time, but the durable checkpoint represented an
uncompiled intermediate carrier.

Source fix:

- after non-final S5 rework, run bounded guarded compile repair before writing the round
  checkpoint;
- record `post_rework_compile` evidence in `round_info`;
- if compile remains broken, merge a hard mechanical compile Issue before checkpointing.

This improves A17 ordering and crash/resume truth.

## R4-F4 — G5 page guard did not control per-round completion

**SOURCE-FIXED; REGRESSION PENDING.**

Per-rework G5 page-guard failure emitted an event but did not participate in `new_pass`.
A Defect Hunter `通过=true` could therefore terminate the rework loop despite a failed
page guard.

The final authoritative `run_g5()` would still catch the page violation, so this was not
a final publication fail-open. It did, however, prematurely consume the bounded repair
opportunity and diverged from R52 ordering.

Source fix:

```
new_pass = page_ok AND defect_hunter_pass
```

A failed page guard can no longer end the current G5 rework loop as successful.
