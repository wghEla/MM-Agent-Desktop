## P1-3 — CANCEL_REQUESTED 与 CancellationToken 是两套互不一致的真相
P1-3 —
    CANCEL_REQUESTED
与 CancellationToken 是两套互不一致的真相
状态机里存在：
    CANCEL_REQUESTED
但 AgentLoop 实际取消判断只有：
    self.cancel.check()
如果数据库已经是：
    CANCEL_REQUESTED
但内存 token 没有 set，AgentLoop 可以继续运行。
反过来 token 已取消，但数据库尚未进入 CANCEL_REQUESTED，也会依赖某一个 check 点才发现。
更危险的是状态竞态：
    "AgentLoop: WAITING_TOOL Canceller: WAITING_TOOL -> CANCEL_REQUESTED AgentLoop: tool 返回 AgentLoop: CANCEL_REQUESTED -> RUNNING"

这一步非法，随后 generic exception 进入
    _fail()
。
而状态表允许：
    CANCEL_REQUESTED -> FAILED
于是一次合法的取消请求可能最后成为：
    FAILED
而不是：
    CANCELLED

SQLite 中的 cancel state 应成为持久化 authority。
CancellationToken 可以作为快速唤醒机制，但每个关键线性化点都要结合 DB owner/CAS。
例如：

不要允许普通 failure path 自动把 cancel request 转成 FAILED，除非记录明确的 cancellation-cleanup failure。

## 3. Focused questions
## Q1. reparse 只检查 parent 链，Windows 下是否存在绕过？

“leaf reparse 指向 workspace 外部”通常会被：
    Path.resolve() + is_relative_to(root)
挡住。
真正的问题不是单纯 leaf，而是：
    scope matcher 使用原 lexical path PathPolicy 使用 resolved path

工作区内 reparse 可以把一个
：
    allowed/link -> denied/

解析后仍在 root 内，因此边界检查通过，而 lexical reparse 已经被
    .resolve()
抹掉。
所以：
    out-of-root confinement
可能仍成立，
但：
    role directory isolation
不成立。

另一个问题是
：
    resolve/check ↓ 攻击者替换目录为 junction ↓ 真正 open/write
当前返回的是字符串 Path，而不是已经验证的 handle，因此这个 race 无法被现在的实现消除。
结论：
    当前实现不足。
优先修：
    lexical reparse walk + handle-based open
## Q2. SQLite 单写者 + threading.Lock，在一个项目一个 driver 下是否够？WAL + FULL 有没有坑？

对
来说，在“一个 driver、所有 DB mutation 都经同一个 Database abstraction”的前提下，基本足够。
但它不能解决：
    同 task 多 coroutine ownership
因为 database serialization ≠ executor lease。
所以当前主要风险不是 SQLite WAL，而是 application-level concurrency protocol。

    WAL + synchronous=FULL
用在本地 NTFS 上是合理的强 durability 默认值，但仍应确认：
    busy_timeout transaction boundaries WAL/SHM/DB 必须同一可靠本地 filesystem checkpoint policy 异常关机恢复测试
不要把项目数据库放在语义不可靠的网络共享盘上再假设与本地 NTFS 一样。
本版最大的 SQLite correctness 问题反而是：
    state transaction ≠ event transaction
即使 SQLite 自身完全正确，也会制造业务层不一致。
## Q3. TaskCancelled / asyncio.CancelledError 是否存在竞态？

主要不是两个 exception handler 本身，而是 cancellation 没有单一 linearization point。
危险窗口包括：
    最后一次 cancel.check() → artifact validation → success commit
如果取消在这期间到达，task 仍可能 SUCCEEDED。
另外数据库：
    CANCEL_REQUESTED
和内存：
    CancellationToken
不一致。
以及：
    WAITING_TOOL -> CANCEL_REQUESTED
可能和 loop 的：
    WAITING_TOOL -> RUNNING
竞争。
当前 generic failure handling甚至可能把取消转成 FAILED。
另外：
    StopReason.CANCELLED
现在还会走成功验收，是独立 bug。
建议以：
    DB state + lease CAS
确定最终 winner。
例如 success commit 必须要求：
    WHERE status='RUNNING' AND owner_token=?

若 cancellation 已把状态 CAS 成
    CANCEL_REQUESTED
，success commit 就必须失败。
这才是可解释的取消竞态语义。
## Q4. glob 的大小写、尾点、UTF-8 等是否有绕过？
最大的绕过目前不是 Unicode，而是：
    reparse alias + raw template substitution
它们都能真正扩大权限。
至于 Windows pathname 语义：

regex 是 case-sensitive，但普通 NTFS 多数目录是 case-insensitive。
这首先造成 policy 和 filesystem identity 不一致。很多情况下表现为“错误拒绝”，但不建议把安全模型建立在这种不一致上。

Win32 pathname normalization 历史上存在 alias 语义，应该直接拒绝 segment：
    foo. foo
而不是尝试兼容。

建议直接拒绝普通路径 segment 中的：
    ":"
除非将来专门实现 ADS capability。

建议拒绝：
    CON PRN AUX NUL COM1..COM9 LPT1..LPT9
及带扩展名的相应特殊形式。

不要假定 Python Unicode regex normalization 等价于 Windows filesystem normalization。
权限规则最好使用经过统一 canonicalization 的 filesystem identity，而不是 UI 输入字符串。


必须按 literal segment 处理，不能允许变量生成
    "* ? ** /"

## Q5. RUNNING→QUEUED 会不会造成重入？

当前：
    RUNNING -> QUEUED
本身可以成为合法的 rate-limit reschedule transition。
但如果没有 owner token：
    Loop A rate-limit → QUEUED Scheduler 立即启动 Loop B 与此同时 Loop A 仍可能执行 finish/cleanup
更关键的是，甚至无需 rate limit：
    已有 RUNNING task 第二个 AgentLoop.run()
就已经能加入执行。
正确模型应是：
    QUEUED --CAS acquire lease--> RUNNING(owner=X) RUNNING(owner=X) --rate limit--> QUEUED(owner=NULL)
旧 executor X 一旦释放 ownership，就不能再修改 task。
所以答案是：
    SQLite lock 不够； run.lock 不够； 需要 task execution lease。
## 4. I1–I10 invariant 审核
    transition_task(..., SUCCEEDED)
可直接绕过
    commit_task_success()
；另外 artifact validation 与 success DB commit 存在 TOCTOU。核心声明目前不成立。
从状态表看
    SUCCEEDED -> *
确实禁止。但
    AgentLoop.run()
仍会在 SUCCEEDED task 上启动新 invocation、执行模型和工具，最终只是不能改状态。因此“状态不可变”成立，“终态不再执行”不成立。
fs PathPolicy 对多数直接路径逃逸有保护；但工作区内 reparse 可穿透 role scope，且
    python.run
可以直接使用宿主 filesystem API 绕开 PathPolicy。
task 会
    RUNNING -> QUEUED
，方向正确；但 invocation 被标 FAILED，attempt 也已经递增，而且没有 lease，回队列存在重入问题。
根据 packet 的 timeout test，对测试中的子进程树有效；但
    taskkill /T
不是强 sandbox/Job Object，也不能证明所有 race 下不会有逃逸/继承进程。v0.2 换 Job Object 是正确方向。
provider schema 只有
    api_key_ref
可以支持“DB 不存 API key”；但
    python.run
继承完整
    os.environ
，所以“密钥不落库”不等于“Agent 无法读取密钥”。数据库声明基本成立，system secret-isolation 不成立。

    enforced vs declared-only

则应把 I1、I4、I5 判为

I2、I3、I6、I7、I9、I10 只能判为

## 5. Release gate 建议
本版本不建议直接 tag 为稳定 v0.1.0。
最少应先关闭以下 release blockers：
    P0-1 禁止 transition_task 直接进入 SUCCEEDED P0-2 修复 lexical reparse / in-root scope bypass P0-3 明确隔离 python.run，或把它诚实降级为高权限任意代码能力 P1-1 task lease / owner CAS P1-2 AgentLoop 严格入口状态，不自动复活状态 P1-3 cancellation DB/token 统一 P1-4 StopReason.CANCELLED 不能验收成功 P1-5 WAITING_TOOL crash semantics P1-6 state + event 同事务 P1-7 artifact sealing / provenance / TOCTOU P1-8 scope variable literalization
修复后至少补这些 adversarial tests：
    "transition_task(RUNNING, SUCCEEDED) 必须失败 allowed junction -> denied directory inside root 必须失败 allowed leaf symlink -> denied file 必须失败 两个 AgentLoop 同时 acquire 同一个 QUEUED task，只能一个成功 第二个 executor 不得调用 provider/tool RUNNING/WAITING_TOOL 上 cancel 与 success commit 并发，只能存在一个最终 winner provider StopReason.CANCELLED + 已有合法 artifact => CANCELLED，不得 SUCCEEDED task mutation 成功而 event insertion 故障 => 整个事务回滚 {question}=\"**\" / \"../x\" / \"a/b\" 等不得扩展 scope verified artifact 在 commit 前被替换 => success commit 必须失败或引用 sealed snapshot WAITING_TOOL crash 后不得无条件重复 non-idempotent tool"
## 最终结论

架构方向是对的：SQLite state truth、显式 task FSM、append-only event、role scopes、artifact-gated success 都是适合作为长期 Runtime 基础的设计。但目前有三个“表面上已经强制、实际上存在旁路”的核心问题：
    SUCCEEDED 可以绕过验收直接写入； 权限 scope 可以被 workspace 内 reparse 别名穿透； python.run 可以完全绕过 fs/path/network 级权限模型。

这三个问题修掉之后，下一优先级不是继续加功能，而是把
四个并发/事务语义钉死。否则到了 v0.3 接真实 Provider、v0.5 上 DAG 之后，这些问题会从“内核 bug”放大成难以复现的跨 Agent 状态污染。
