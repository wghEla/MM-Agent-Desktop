## P1-1 — Issue Ledger repair identity was still incomplete

### Finding

Before reviewer patching, `IssueLedger.收回执()` still accepted a receipt with no
`generation`, generated a random UUID when `receipt_id` was missing, and counted
attempts across generations. Explicitly re-reported shelved issues also remained shelved,
because `并入()` reopened only `已消解`.

`回退轮修订()` also reverted state without advancing generation, allowing a delayed
verdict from the reverted generation to become valid again after a later receipt.

These are replay / stale-event correctness defects and can produce premature fuse or
false resolution.

### Reviewer patches already applied

- `4a2f790` — strict receipt generation / stable id / generation-local attempt budget;
  shelved reappearance reopens; rollback advances generation.
- `b3e3792` — distinguishing tests for missing identity, stale receipt, generation-local
  attempt budget, shelved reappearance and rollback stale verdict.
- `312167a`, `bcc1433` — S5 orchestrator owns deterministic receipt identity and
  restricts receipts to the issues actually assigned to that repair leg.

### Status

**SOURCE PATCHED — REGRESSION PENDING**

Do not mark CLOSED until current-head focused + full regression is green.

## P1-2 — G5 R49-R52 rework is not part of the authoritative product path

### Finding

`PaperFoundryEngine` calls `run_g5()` directly. It does not call
`run_g5_rework()`.

Therefore A20 cannot be MATCH merely because a rework function exists.

Additionally, the rework function had a deterministic restore bug:

- S5 writes `台账/审稿台账.json` as a top-level list.
- `run_g5_rework()` attempted `data.get("条目", [])`.
- It then treated dataclass `Issue` as a Pydantic model via `Issue.model_fields`.
- A broad `except Exception: pass` converted those failures into an empty ledger.

### Reviewer patch already applied

- `396f515` — restore S5 ledger through `IssueLedger.从快照()` and fail closed on
  malformed carrier shape.

### Remaining blocker

The rework loop is still not publication-complete:

1. authoritative Engine does not invoke it;
2. writer / plotter rework does not feed repair receipts back through the ledger;
3. defect-hunter recheck is reduced to a boolean and does not perform paired issue
   verdict transitions;
4. in-memory ledger mutations are not durably written back before final
   `check_g5()`;
5. final acceptance therefore is not evidence that R49-R52 actually resolved the
   blocking issue set.

### Status

**OPEN P1**

## P1-3 — S5 hard/correctness fuse escalation is marker-only

### Finding

For `硬伤/正确性` fuse candidates, `run_s5()` only appends the issue id to
`needs_escalation`.

That list is restored, checkpointed and returned, but no S5 executor consumes it.
There is no actual one-time “change route / change context / redo” escalation.

On the final review round, the code also exits on `round_num >= max_rounds` before the
fuse-candidate processing block.

The existing `test_fuse_escalation_for_blocking` proves only that an issue becomes a
fuse candidate; it does not prove an escalation is executed.

### Status

**OPEN P1**

A17 and B7 must remain PARTIAL until this is closed.

## P1-4 — `交接/降级放行.json` has two incompatible contracts

### Finding

S2 writes:

```json
{"问题": [{"问题编号": 1, "issues": ["..."]}]}
```

G5 checks shelved review blockers using:

```json
{"issue_ids": ["审-..."]}
```

(or the alias `条目`).

No production path was found that writes the G5 issue-level shape.

As a result, the same carrier name represents two unrelated schemas and the G5
degraded-release path cannot be mechanically satisfied by the normal S5/G5 pipeline.

### Status

**OPEN P1**

Define one typed runtime-owned degraded-release contract with separate question-level and
review-issue-level entries. Degraded release must remain distinct from PASS.

## P1-5 — S6 can modify the paper after G5 and deliver without re-gating

### Finding

Pipeline order is:

`G5 PASS → S6 page review → Writer/Plotter fixes → final compile → harvest`.

S6 repair roles can modify `论文/*.tex` and figures. After those changes the code checks
compile success, but does not rerun the publication invariants that G5 had certified:

- G4 structural/audit checks;
- stale-value checks;
- page guard;
- ledger publication state;
- final defect verification.

The final delivered PDF is therefore not necessarily the same revision that passed G5.

This is a publication TOCTOU.

### Status

**OPEN P1**

At minimum, after S6 changes and final compile, rerun mechanical G5 against the S5b page
baseline. Prefer a final defect-hunter verification too. Harvest must occur only after
that terminal verification passes.

- A6 compares two local SHA256 values; it does not execute red-team recomputation.
- A11 manually creates three tasks; it does not execute the escalation swarm.

- B9 intentionally accepts that section-title removal is not detected.
- B12 asserts that the old number is still present in a string instead of driving the
  actual propagation chain.
- B14 tests only `all_downstreams()`, not durable invalidation + crash/restart + rerun.

This evidence is useful as smoke/static coverage but is not sufficient to promote the
full fidelity mechanism to MATCH.

## P2-1 — Repair receipt schema classes are not enforcing the production carrier boundary

`RepairReceipt`, `BeautyReceipt`, `G5RepairReceipt` and `S6TerminalReceipt` exist,
but S5/S5b/G5/S6 repair artifacts are generally declared as plain
`ExpectedArtifact(rel_path=...)` without those schemas.

For S5, the strict ledger + runtime-owned identity patches reduce correctness risk, but a
malformed semantic receipt can still be sealed as a successful task before the ledger
rejects it.

Recommendation: distinguish model-output draft schema from runtime-enriched ledger event
schema, and validate both at their respective boundaries.
