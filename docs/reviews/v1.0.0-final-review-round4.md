P1-1 — generation CAS 仍是可选的，而且放在 batch 参数上，不是真正的消息身份

现在：

Python
运行
def 收裁定(..., expected_generation: int | None = None):
    ...
    if expected_generation is not None and x.generation != expected_generation:
        continue

所以：

Python
运行
expected_generation=None

时实际上 完全没有 CAS。

所谓“未提供时使用当前 generation”在代码里并不存在；它实际上等价于：

无论这条 verdict 原来属于哪个 generation，都把它当成当前 generation。

于是旧裁定仍可：

gen0 已消解
→ reopen → gen1 待改
→ gen1 receipt → 待复核
→ 延迟的 gen0 verdict，不传 expected_generation
→ gen1 被置 已消解

而且 expected_generation 是整个 batch 共用一个参数。如果：

Issue A generation=0
Issue B generation=2

同一批 裁定们 本身无法分别携带正确 CAS generation。

正确形态应当是每条 verdict 自带 generation：

Python
运行
{
    "id": "意-1-01",
    "generation": 2,
    "裁定": "已消解",
}

然后严格：

Python
运行
if r["generation"] != x.generation:
    stale

generation 不应该可省略。对 crash-recovery correctness path，missing identity 应 fail-closed，而不是 best-effort。

P1-2 — receipt 仍然没有绑定 generation；fallback receipt_id 也不具备幂等性

现在 fallback：

Python
运行
receipt_id = str(r.get("receipt_id", "")) or \
             f"{x.id}:attempt{x.尝试次数 + 1}"

第一次请求没提供 receipt_id：

意-1-01:attempt1
尝试次数 → 1

同一个请求 crash 后重放、仍没 receipt_id：

根据当前计数自动生成：
意-1-01:attempt2

所以它不会被去重。

也就是说：

“调用者提供 receipt_id 时幂等”成立；
“自动生成 receipt_id 时幂等”不成立。

更关键的是 receipt 完全没有 generation CAS。

因此 gen0 的迟到 receipt，在 gen1 reopen 后到达：

issue gen1 / 待改
↓
旧 gen0 receipt
↓
尝试次数 += 1
状态 → 待复核

这已经让旧 generation 的消息推进了新 generation 状态。

所以 identity 应贯穿：

(issue_id, generation, attempt_id/receipt_id)

而不只是 verdict 最后一跳有 generation。

建议干脆要求：

Python
运行
{
    "id": "...",
    "generation": 1,
    "receipt_id": "...",
    ...
}

两个字段缺任一都拒绝。

P1-3 — 尝试次数 是跨 generation 累计的，因此新 generation 可以零修改直接熔断/搁置

这是当前一个很明确的假收敛路径。

例如 gen0：

尝试2 → 待复核 → 已消解

此时：

Python
运行

之后问题重新出现：

运行

代码只做：

Python

x.状态 = 待改

没有重置 generation-local attempts。

因此刚进入 gen1，什么都还没修改：

Python
运行
x.状态 == 待改
x.尝试次数 == 2

立刻：

Python
运行
搁置条目(x.id, "两次仍未解决")

会成功。

然后 blocker 被排除在 收敛() 之外。

所以当前实际语义是：

“这个 Issue 生命周期里曾经修改过两次”

而不是你原本需要的：

必须二选一：

或者更干净地使用：

并让 熔断候选/搁置条目 只看当前 generation。

P1-4 — 已搁置 Issue 再次明确出现时不会 reopen，会被永久吞进搁置态

_find_match() 有一个很微妙的不对称。

首先显式对应：

Python
运行

if 对应:
    for x in self.条目:
        if x.id == 对应:
            return x

这里 没有排除 搁置。

后面的 heuristic matching 才有：

Python
运行

    continue

于是一个已经搁置的硬伤，如果下一轮 reviewer 明确说：

Python
运行

    "对应": "意-1-01",
    "问题": "该硬伤仍然存在"
}

会匹配到旧 Issue。

但 并入() 只对：

进行 reopen。

搁置 不满足条件，因此它仍然保持：

只是历史里多一条“问题仍存在”。

而 收敛() 又不把搁置算 blocker。

结果就是：

reviewer 明确重新报告一个已经搁置的硬伤，系统仍然可以保持 convergence=True。

这是直接的假收敛。

比较合理的规则应当是：

已消解 + 新报告 → reopen
搁置 + 新报告 → reopen

二者都：

尤其显式 对应=id 的新报告，不能静默留在搁置态。
